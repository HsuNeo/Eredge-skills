# 中文润色与去模板化

把文字改得具体、顺口、符合使用场景。这里的“去AI味”是编辑表达，不是检测作者身份；不承诺任何 AI 检测分数。

## 先确定修改范围

- 读完原文再改，优先遵守用户指定的受众、语气、字数、用途和保留内容。只改一句就只改一句；轻改不默认重写整篇。
- 公告、说明书和正式材料可以保持严谨。自然表达不等于改成段子、口头禅或故意加入语病。
- 没有原文却要求“润色”时，请用户提供原文；不能把自行创作冒称对原文的修改。用户明确要求从零起稿则按其资料起草。

## 修改方法

1. 保留信息：名称、数字、日期、链接、功能边界、限定条件、作者观点和必要行动要求不丢失。修改事实错误时说明依据；未核实的新结论不混进正文。
2. 先理顺关系：让每段集中处理一个意思，连接条件、原因和结果；已有清楚的结构不为变化而打乱。
3. 换掉空泛表达：把没有信息量的赞美、抽象口号和生硬套话改成原文支持的具体动作、问题或结果。缺少依据时删去夸大成分，不虚构数据、体验或案例补空。
4. 调整语气：拆解过长的句子，保留完整意思；长短句自然交替，不把每个短语都单独换行。不机械添加反问、感叹、三句排比和“首先、其次、最后”。确有顺序的操作步骤可以编号。
5. 朗读检查：删重复、绕口和翻译腔，核对说话者身份。原稿中的第一人称经历可以保留，不把普通描述改成“我亲测”“我们客户都说”。

## 按场景取舍

- 公众号与短文：尽早进入具体问题，段落便于手机阅读。原文有真实场景就保留，没有就不编故事。结尾互动与行动要求按用途保留，不固定凑关注、点赞、收藏。
- 产品说明：优先说明在哪里操作、能做什么、有哪些限制；保留截图/GIF位置、产品链接和必要步骤。不把功能介绍改成未证实的效果承诺。
- 正式通知：保留时间、地点、对象、要求与必要礼貌，压缩套话即可。需要严肃表达时，不强行口语化。

## 输出

默认直接给修改后的文字。用户要求对照时，再给原文、修改后及简短原因；只问哪里不顺时先回答问题，不擅自改整篇。

说明风格的示例见 [修改前后对照](references/examples.md)。本技能可独立使用，不依赖 `humanizer` 或 `humanizer-zh`，也不包含第三方同名项目的 CLI 或规则引擎。
